# 信源调研与抓取方法

线上核实事实（创刊时间、出版主体、最新期数、是否仍在出版）的路子，
都是实际验证过的，能少走弯路。

- **善用 Google AI Mode**：事实性问题（如搜「《刊名》 創刊」）直接用 AI Mode
  （`https://www.google.com/search?q=<查询>&udm=50`），比逐页翻搜索结果快得多；
  AI 给出的结论要点开原文交叉验证后再写入档案，无确证不推算。
- **需要人工介入时及时提出**：遇到验证码、登录墙、环境异常墙时不要卡住重试，
  立即把待操作的链接和需要用户做的动作说清楚（如「请在浏览器里通过这个验证码」），
  人工通过后继续。2026-09 创刊时间调研即靠「AI Mode + 用户过验证码」完成 24 种核实。
- **善用 Firecrawl 抓取**（媒介素养项目验证过的路子）：JS 渲染、需要等待加载
  或被一般抓取方式拦住的页面，用 Firecrawl 拿干净的 markdown；需要点击、翻页、
  登录后才能看到的内容，用它的浏览器交互模式走完流程再抓。
- **gov.tw 等被拦站点：本机打不开 ≠ 信源失效**。台湾 gov.tw 站点从大陆网络普遍被拦
  （DNS SERVFAIL、TLS SNI 阻断、Cloudflare WAF 403 三种形态，本机代理出口异常时也
  借不上力）。判定方法：搭临时 GitHub Actions 工作流在 CI 机房实测（2026-09 实测
  27 条官方信源 18 条 200 可达），可达的通道一律保留，交给「新刊速递」CI 双周抓取
  自然验证；结论已固化在 tools/fetch_issues.py 文档串。
- **微信公众号**：mp.weixin 的环境异常墙拦机房 IP，CI 不抓；单篇用
  tools/fetch_wechat.py 在本机登记（住宅 IP 直过），或走搜狗搜索低置信补充
  （限流极凶，一次运行只发一个请求，详见该脚本文档串的试点结论）。

## 数据批处理的配套方法

- **批量编辑先核原文再替换**：批量改动前先 `grep` 确认该处的实际文本（简繁转换、
  标点全半角都可能让「以为的原文」不存在），替换用「断言唯一命中」的脚本方式防误伤。
- **简繁残留检测**：用 OpenCC 反向验证（`convert(text) == text`），不要自建繁体
  字集——简繁同形字会让字集法误报一大片。
